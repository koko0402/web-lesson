作り方の型

「何か作りたい」から「完成」までの手順書。DAY 7 の内容を、何度でも使える形にまとめた。 新しいものを作るたび、この紙をなぞって。

A. 考えるB. 固めるC. 作る D. 育てるAIの使い方ワークシート
いちばん大事なこと 大事なのはイメージ。どういうものを作りたいか。そのために何がいるか。どう動くのか。 そこさえ決まっていれば、コードは最悪AIでもどうにかなる。決まっていなければ、誰にも頼めない。

A. 考える

1. どういうものを作りたいか、明確にする

一言で言えるレベルまで。かっこいい企画書は要らない。「手札のことば並べて、いちばん笑えたプロポーズが勝ちってだけのバカゲー」 で十分。

そのうえで、この4つに答える。

問い答えると決まること
誰が使う？画面の作り、難しさの加減
いつ・どこで使う？PCかスマホか、1台か複数か
何がいちばん楽しい／便利？いちばん力を入れるところ
1回どのくらいで終わる？ボリューム、データの量

2. 欲しい機能を言語化する

「〜できる」の形で、思いつくまま書き出す。順番も重要度も気にしない。

そのあと、今回はやらないことを決める。判断基準は「これが無いと成立しないか？」。 成立するなら、それは後回しでいい機能。

やらないことを決めるのが、完成させるコツ 全部入れようとすると、永遠に完成しない。後から足せる。

3. そのために必要なものを挙げる

機能を、画面の部品と技術に分解する。表にすると抜けが見つかる。

欲しい機能必要な部品（画面）必要な仕組み（技術）
ことばが配られる手札のカードMath.random ＋ 配列
今の状況を覚える—game オブジェクト
勝ち負けが決まる結果画面if / else if

ここで「知らない技術」が出てきたら、その時点で調べる。作り始めてから気づくと、設計をやり直すことになる。

B. 固める

4. システムの流れを、わりと詳細に決める

「このボタンを押したらこうなる」を、順番に書き出す。面倒がらずに細かく書くと、あとの実装がほぼ写経になる。

書けないところ＝分かっていないところ 手が止まったら、そこがまだ決まっていない部分。 コードを書く前に見つけられたのはラッキー。

5. 問題点を挙げる

「こうしたらバグるかも」を先に書き出す。ここがいちばんコスパの良い工程。 作ってから見つけると直すのが大変だが、作る前なら最初から入れるだけ。

こうなったら困る対策
同じことばが手札に2枚くる配るときに重複をはじく
指輪が0より減る0になった時点で終わらせる
ボタンを連打される処理中は押せなくする
入力が空っぽ初期値を入れる

表の右の列が、そのままプログラムに書くべき条件になる。

6. 調べる・相談する

分からない部分は、この段階で調べる。「これあると良いよ」という提案をAIから引き出して、 良ければ取り入れる。ただし採用するかは自分で決める（→ AIの使い方）。

7. 図や文で、1度まとめる

処理の流れをアクティビティ図にする。四角が処理、丸っこいのが分かれ道、矢印が流れ。ルールはこれだけ。 ノートに手書きで十分。

図にすると見えるもの 分かれ道の数＝if の数／戻る矢印＝ループ／箱1つ＝だいたい関数1つ。
ここまで来たら、コードは図を訳す作業になる。

C. 作る

8. 作る順番を守る

  1. データを決める（配列・オブジェクト・state）
  2. 表示だけ作る（画面に出る。まだ動かない）
  3. 操作を付ける（ボタン、判定）
  4. 演出を足す（アニメーション、色、効果）
逆順にやると地獄 先に見た目を作り込むと、データ構造を変えたときに全部作り直しになる。 見た目は最後。

9. 各段階で必ず動かす

1つ書く → 保存 → F5 → 確認。この往復を細かく。 全部書いてから初めて開く、は絶対にやらない。どこで壊れたか分からなくなる。

10. エラーを直す

F12 を開いて Console を見る。赤い文字のいちばん上を読む。 分からなければ、エラー文と該当コードをそのままAIに貼る。 くわしくは エラー辞典 へ。

11. 動いたら、動いたファイルを取っておく

index_ok.html のような雑な名前でコピーを残しておくと、 壊したときに戻れる。

D. 育てる

12. 1週間くらい、自分で触る

動いた時点では、まだ半分。しばらく使ってみると 「これ要るな」「これ邪魔だな」が必ず出てくる。それを直す。

13. 友達に触らせる

自分では絶対に気づけないことが、他人が触ると3分で出てくる。 説明せずに渡して、黙って見ているのがコツ。 説明したくなった時点で、それは「説明が要る作り」だという発見。

自分以外が触る目線 説明なしで分かるか？　押せると分かるか？　間違えても壊れないか？
これを考えられる人は、一気に上手くなる。

14. また直す。2〜3周したら完成

完璧を目指すと永遠に終わらない。どこかで「完成」と言い切るのも技術のうち。

AIの使い方

○ 伸びる使い方× 伸びない使い方
  • エラー文をそのまま貼って「これ何？」と聞く
  • 仕様を説明して「抜けている考慮点は？」と聞く
  • 「こういう機能を足したい。何が必要？」と相談する
  • 書いたコードを貼って「もっと短く書ける？」
  • 大まかな下書きを出させて、自分で読んで直す
  • 面倒な繰り返し部分だけ書かせる
  • 丸投げして、出てきたコードを読まずに貼る
  • 動かないとき、理由を見ずに何度も作り直させる
  • 何を作りたいか決まっていないのに聞く
  • 出てきた「あると良い機能」を全部入れる
プロも使っている 下書きを出させたり、面倒な部分を任せるのは普通のこと。大事なのは 出てきたものを判断できる自分でいること。丸投げすると、結局直せなくて止まる。

そのまま使えるプロンプトの型

「コードはまだ書かなくていい」と付けるのがポイント。設計の相談相手として使うと、いちばん役に立つ。

質問文を作るツールがある AIへの質問文メーカー で空欄を埋めると、 場面に合わせた質問文が自動でできる。慣れるまではこれを使って。
