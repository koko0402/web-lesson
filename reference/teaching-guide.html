教える側の進行メモ

各回の時間配分、詰まりやすい所、そのときの声かけ。
これは教える人だけが見る資料。

基本の進め方毎回の準備各回のメモ 詰まったときの対応言い方のコツ

基本の進め方

1回の組み立て（60〜90分）

時間やることポイント
0〜5分前回のふりかえり前回作ったものを開いて見せる。話すより見せる
5〜10分今日のゴール完成イメージのスクショを見せる。「今日これが作れる」
10〜35分説明（スライド前半）25分が限界。それ以上は入らない
35〜75分実習（章扉のあと）ここが本体。黙って見る時間を作る
75〜85分詰まった所の共有「どこで止まった？」を聞く。直し方を一緒に
85〜90分まとめ・宿題チェックリストに印を付けてもらう
いちばんやりがちな失敗 説明を最後まで通してから実習に入ること。
前半を全部聞いた時点で、最初のほうは忘れている。説明はスライド1〜2枚ごとに切って、 すぐ打たせるほうが定着する。時間が足りなければ、説明を削って実習を残して。

毎回のリズム

この3つを体で覚えてもらうのが、9回を通しての裏テーマ。

  1. 書く → Ctrl+S → F5 をこまめに。まとめて書かせない
  2. 動かなくなったらまず直前に足した所を消す
  3. 分からなければF12を開く

毎回の準備（5分）

  • その回のスライドを開いて、F で全画面にしておく
  • practice/ の該当フォルダを VSCode で開いておく（見せる用）
  • 相手のPCで前回のファイルが開けるか、最初に確認する
  • 電源・ネット・画面共有の確認
相手の画面が見えるようにする 横に並ぶか、画面共有してもらうか。相手の手元が見えないと、詰まりに気づけない。 「できた？」と聞いても、たいてい「はい」と返ってくる。

各回のメモ

DAY 0はじめに・道具をそろえる

目的：手を動かす前に「何を作るのか」を共有し、環境を整える。

  • 時間の大半はインストールに取られる。事前に はじめての準備 を渡して、 当日までに済ませてもらうと1回分浮く
  • 最終作品（パーティゲーム）を実際に遊ばせる。ここでやる気が決まる
  • 「なぜPythonじゃないのか」は、聞かれる前に説明しておくと後がスムーズ

詰まりポイント：拡張子が見えていない／インストール時のPATH／管理者権限

今日はまだプログラムは書かない。道具を用意するだけ

DAY 1HTMLだけでサイトを作る

目的：タグの形に慣れる。「保存して開く」の往復を体に入れる。

  • 見た目が地味なので、「今日はダサくていい」と最初に宣言しておく
  • Emmet（! + Tab）は最初に教えると感動される
  • 実習は「見本を写す → 自分の内容に書き換える」の2段階。書き換えまでやらせる

詰まりポイント：全角の記号（最頻出）／終了タグの閉じ忘れ／画像のパス／改行されない

色が付いてないタグは、たぶん全角が混ざってる

DAY 2ページを増やす・表・フォーム

目的：1枚のページを「サイト」にする。パスの感覚をつかむ。

  • 同じ nav を3ページに貼るのは面倒だが、その面倒さを味わってもらうのが狙い
  • 表は Emmet で骨組みを出させると速い
  • フォームは「今は送れない」を必ず言う。言わないと後で混乱する

詰まりポイント：リンク先のファイル名／表のマス数がそろわない／img フォルダのコピー忘れ

DAY 3CSS ① 色・文字・余白

目的：見た目が変わる楽しさを体験する。ボックスモデルを理解する。

  • 最初に body の背景色だけ変えさせて、link が効いているか確認させる。 ここを飛ばすと、あとで原因の切り分けができない
  • ボックスモデルは図で説明してから、実際に padding を大きくして見せる
  • ここで初めて「楽しい」と言われる回。時間を多めに取っていい

詰まりポイント：link の書き忘れ／セミコロン／. や # の付け忘れ

効かないときは、まず F12 で検証。取り消し線が付いてたら負けてる

DAY 4CSS ② 並べる・動かす

目的：Flexbox で「作れる人の見た目」にする。

  • 「親に書く」を何度も繰り返す。ここだけは丸暗記でいい
  • hover の演出は反応がいいので、早めに1つ作らせる
  • レスポンシブは窓を細くして見せるのが一番わかりやすい

詰まりポイント：子に flex を書いてしまう／box-sizing を入れず幅がずれる／ 中央寄せが効かない（width がない）

DAY 5JavaScript ① 動きの基本

目的：「取ってくる → 何かする → 書き戻す」の型を入れる。

  • 1個目のボタンが動くまで、次に進まない。ここが全体の分岐点
  • 動いた瞬間に「今、プログラムを書いた」と言ってあげる
  • C言語の経験があるなら、対応表（JS構文一覧）を見せると安心される

詰まりポイント：null（idのスペル／scriptの位置）／"5"+1／ = と ===／大文字小文字

エラーは敵じゃない。場所と理由が書いてあるので、読めば9割わかる

DAY 6JavaScript ② データを扱う

目的：「データを直す → 描き直す」という設計の考え方を入れる。

  • ここが技術的には一番の山。焦らず、①の配列→リストだけで1時間使ってもいい
  • innerHTML = "" を忘れさせてわざと増え続けさせると、意味が体でわかる
  • 次回の宿題（作りたいもの3つ）を必ず出す。これが無いと DAY 7 が成立しない

詰まりポイント：描画関数の呼び忘れ／リストが増え続ける／保存が [object Object]

DAY 7総合制作（この講座の山場）

目的：文法ではなく作り方の手順を教える。ここだけは他で教われない。

  • コードを書く時間より、紙に書く時間を長く取る。 STEP 1〜7 を相手の「作りたいもの」で実際にやらせるのが理想
  • 宿題の「作りたいもの3つ」を出させて、その1つを題材に STEP を通す
  • 最終作品のコードは読ませるだけでよい。全部書かせる必要はない
  • 時間が足りなければ2回に分けてください。ここを急ぐと意味がなくなる

相手が固まったら：「誰が使う？」「何が楽しい？」の2つを聞くと、たいてい動き出す。

作りたいものが決まってれば、コードは最悪AIでもどうにかなる。逆は無理

DAY 8直す・公開する・これから

目的：自分で直せる／人に見せられる状態にする。

  • わざとバグを仕込んだファイルを用意して、直させると実践的 （練習問題集 のデバッグ問題が使える）
  • GitHub のアカウント作成は時間がかかるので、事前に作ってきてもらう
  • 公開前に個人情報と画像の権利を必ず確認させる
  • 最後に「次に何を作るか」を言わせて終わる

詰まったときの対応

すぐ答えを言わない いちばん大事。答えを言うと、その場は進むが力にならない。 次の順番で誘導して。
  1. 「どこまで動いてる？」 … 問題の範囲を切らせる
  2. 「F12 になんて出てる？」 … 自分で読ませる
  3. 「何行目って書いてある？」 … 場所を特定させる
  4. 「そこ、何をしようとしてる？」 … 意図を言語化させる
  5. それでも詰まったら、選択肢を2つ出す（答えではなくヒント）
  6. 5分たっても進まなければ、答えを見せて先に進む。詰まり続けるほうが害
こう言われたらこう返す
「動きません」「どこまでは動いてる？」
「エラーが出た」「なんて書いてある？　読んでみて」
「わからない」「何をしたいかは分かってる？」（目的と手段を分ける）
「これでいいか？」「動いた？　動いたなら正解」
「センスない」「今のは道具の使い方の問題。センスは関係ない」

言い方のコツ

○ 効く言い方

  • 「これは覚えなくていい。調べればいい」
  • 「全部おぼえてる人はいない」
  • 「エラーが出るのは正常」
  • 「今のは打ち間違い。よくある」
  • 「動いたね。それが正解」
  • 「1個ずつ試そう。まとめてやると原因がわからなくなる」

× 避けたい言い方

  • 「簡単だよ」（できないと落ち込む）
  • 「さっき言ったよね」
  • 「なんでそうなるの？」（責めに聞こえる）
  • 「普通は〜」
  • 専門用語を説明なしで使う
  • 相手のキーボードを勝手に触る
初心者が本当に困っているのは、たいてい文法ではない 全角が混ざっている、保存していない、ファイルの場所が違う。
こういう「本に載っていない所」で止まっている。 教える側がここを先回りできると、進み方がまるで変わる。 → パソコンとファイルの基本 を最初に渡しておくのが効果的。
